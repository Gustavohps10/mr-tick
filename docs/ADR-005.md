# ADR-005 — Sincronização Local-First com Reconciliação de Exclusões para Fontes Legadas e Canais de Stream

## Status

**Proposto**

## Data

16 de Setembro de 2026

## Autor

Gustavo Henrique Pereira dos Santos

---

## 1. Contexto

O ecossistema Mr-tick adota uma arquitetura *local-first* baseada em RxDB, onde os dados operam primeiro localmente no cliente e sincronizam bidirecionalmente com sistemas remotos através de conectores de *Data Sources* (ex: Redmine, Jira, GitLab, GitHub, etc.).

### 1.1 Limitações de Fontes de Dados Corporativas Legadas
Fontes de dados amplamente utilizadas no ambiente corporativo (como instâncias internas de Redmine) apresentam fortes restrições arquiteturais:
- **Ausência de Webhooks, SSE ou WebSockets**: O cliente não recebe notificações push quando alterações ocorrem remotamente.
- **Hard Deletes na Origem**: Ao apagar um registro (ex: apontamento de horas ou tarefa), a API/banco de dados remoto remove a linha física (`DELETE FROM ...`), sem manter *tombstones* (`deleted_at`).
- **Incompatibilidade com Replicação Pura por Checkpoint**: Em replicações baseadas em `updatedAt > checkpoint`, registros deletados no remoto não aparecem no lote de atualização. Consequentemente, o banco local do RxDB mantém registros apagados indefinidamente como "registros zumbis".

### 1.2 Oportunidade de Conexão Direta em Desktop
No ambiente desktop (Electron), o processo principal (Node.js) tem a capacidade de estabelecer conexões de rede locais e acessar protocolos de banco de dados diretamente caso o usuário corporativo possua credenciais *readonly* na infraestrutura da empresa.

---

## 2. Decisão

Adota-se uma estratégia de sincronização em duas camadas complementares, com suporte a reconciliação periódica de exclusões e extensibilidade para canais de *stream* em tempo de execução.

### 2.1 Camada 1: Sincronização Incremental Rápida (Live Polling)
- **Objetivo**: Puxar criações e edições recentes com baixo custo de rede.
- **Mecanismo**: Utiliza o motor de replicação HTTP do RxDB (`replicateRxCollection`) com estratégia de checkpoint (`updatedAt` + `id`).
- **Frequência**: Intervalo curto (ex: a cada 1 a 5 minutos) ou disparado sob demanda do usuário.
- **Tratamento de push**: Modificações locais são enviadas via `push.handler` diretamente para os serviços do OpenAPI / provedor do conector.

### 2.2 Camada 2: Reconciliação por Varredura de Janela Ativa (Sweep Window)
- **Objetivo**: Detectar e remover registros que foram excluídos com *hard delete* no servidor remoto.
- **Janela de Observabilidade**: Varredura restrita ao período operacional ativo (ex: últimos 30 a 60 dias, ou mês corrente), evitando requisições exaustivas de todo o histórico.
- **Algoritmo de Reconciliação**:
  1. A aplicação solicita à fonte remota a listagem de IDs existentes na janela de datas:
     `IDs_Remotos = ObterIDs(janelaInicio, janelaFim)`
  2. O banco local RxDB extrai todos os IDs armazenados correspondentes à mesma conexão e janela:
     `IDs_Locais = RxDB.find({ connectionInstanceId, data: [janelaInicio, janelaFim] }).map(doc => doc.id)`
  3. Identifica a diferença de conjuntos:
     `IDs_Deletados = IDs_Locais \ IDs_Remotos`
  4. Para cada item em `IDs_Deletados`, marca o documento como removido no RxDB local (`_deleted: true` ou `doc.remove()`).
- **Frequência**: Executada na inicialização do workspace, em intervalos espaçados (ex: a cada 30 a 60 minutos) ou explicitamente ao acionar "Forçar Sincronização".

### 2.3 Evolução Futura: Direct Database Profiler / Tail Reader (pull.stream$)
Para ambientes corporativos onde o usuário possui credencial *read-only* de banco de dados (ex: MySQL/Postgres do Redmine on-premise):
- **Arquitetura**: O processo `main` do Electron executa um watcher leve e indexado via SQL (`SELECT id, updated_on FROM ... WHERE updated_on > :lastCheck`) em polling de baixa latência (sub-segundo).
- **Integração com RxDB**: As emissões desse leitor são enviadas via canal IPC para a janela de renderização, alimentando o `pull.stream$` do RxDB Replication.
- **Resultado**: Converte uma fonte originalmente passiva/legada em uma experiência *real-time* de latência quase nula, sem onerar a API HTTP web do servidor.
- **Fallback**: Ambientes Web ou usuários sem acesso direto ao banco continuam utilizando a Camada 1 e 2 via HTTP REST tradicional.

---

## 3. Consequências

### Positivas
- **Consistência garantida**: Registros deletados no remoto deixam de ficar órfãos no banco local.
- **Respeito à infraestrutura remota**: A reconciliação opera apenas na janela ativa, sem necessidade de varrer anos de histórico legado.
- **Agnóstico a conectores**: Funciona com qualquer conector (Redmine, Jira, Fake, etc.), mesmo sem suporte nativo a webhooks.
- **Caminho claro de otimização**: Abertura formal para que addons Pro ou corporativos pluguem streams via banco de dados sem alterar a arquitetura do Core.

### Negativas / Mitigações
- **Custo adicional de requisição na reconciliação**: Mitigado solicitando apenas conjuntos de IDs/datas ao invés de carregar a entidade completa no momento da varredura.
- **Frequência de sweep**: Deve ser calibrada para não saturar limites de taxa (rate limiting) de APIs corporativas.
