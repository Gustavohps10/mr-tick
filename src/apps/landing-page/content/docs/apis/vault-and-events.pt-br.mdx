Um addon pode precisar lembrar preferências, guardar um valor privado ou reagir quando o timer começa. Este guia explica onde manter cada tipo de informação e como receber essas notificações.

O aplicativo gerencia as credenciais usadas para conectar contas externas por `core.connections`. Use `host.vault` para outros valores privados do addon e para ler configurações salvas; não crie outro armazenamento para os tokens da mesma conta.

## Escopos explícitos

- `{ kind: 'addon' }`
- `{ kind: 'workspace', workspaceId }`
- `{ kind: 'connection', workspaceId, connectionInstanceId }`
- `{ kind: 'capability', workspaceId, connectionInstanceId, capabilityId }`

`get(scope, key)`, `set(scope, key, value)` e `delete(scope, key)` retornam `Either`, que representa sucesso ou falha. Uma string privada ausente é `null`. Informe explicitamente a qual addon, workspace, conexão ou capability o valor pertence. O aplicativo valida o acesso a esses dados; a tela aberta pelo usuário não escolhe esse destino automaticamente. O uso de uma capability no armazenamento não exige uma nova declaração no manifesto.

## Configurações declarativas

Descreva os campos de configuração com `contributions.settings.register(schema, { onApply })`. Para ler configurações que não são secretas, use `host.vault.getSettings(scope)`: o resultado inclui os valores salvos e o número da revisão. `onApply` recebe o destino (`scope`), a revisão (`revision`), os valores (`values`), os eventos (`events`) e `track`, que registra recursos para limpeza. Não armazene essas configurações como se fossem credenciais privadas.

## Inicialização e limpeza

Registre as integrações e retorne de `activate`; esperar pelo estado `ready` nessa etapa pode bloquear a inicialização. `core.runtime.onStateChanged` informa imediatamente o estado atual e depois as mudanças entre `starting`, `ready`, `restarting` e `closed`. O estado `ready` indica que os serviços locais estão prontos, mas a busca de dados externos pode continuar em andamento.

O host limpa contribuições e listeners registrados na desativação ou ativação com falha. Feche sockets, clientes e jobs próprios. Trocar workspace não desativa o addon.

## Eventos garantidos

`timer:start`, `timer:pause`, `timer:resume`, `timer:stop`, `timer:update`, `workspace:changed`.

Esses eventos informam mudanças enquanto o addon está ouvindo; eventos anteriores não são reenviados e não há atualização garantida a cada segundo. O SDK não oferece eventos gerais de inatividade ou de qualquer alteração em apontamentos. Use `context.core.timer` e `context.core.timeEntries` para consultar ou alterar esses dados, informando o workspace e os identificadores da operação. Para autenticação de contas externas, consulte [autenticação](/pt-br/docs/capabilities/auth).
